    The problem this follow-up answers

    In home-actions-a.html, record-button sat immediately to the right of home-search-field, inside the same row, the same height, the same corner radius family as the field's own trailing edge. The owner's read: that position is where a search bar's "go" or "submit" control conventionally sits (iOS's own keyboard return key, most search UIs), so Record's proximity there borrows that meaning even though Record does something unrelated. All three variants below are candidate fixes to that one relationship — nothing else about Option A (model, copy, R1–R13) is reopened.

    A1 — stacked, Record above the field

    record-button takes its own full-width row; directly below it, home-search-field takes the very bottom row — the iOS 26 search position (brief §5). Typing hides the Record row entirely (crossfades out) and leaves the search row with cancel-search-button.

    44pt: both rows are 44pt tall on their own, full width — the largest tap area of the three. VoiceOver order: visually Record is read before the field (top row before bottom row); the brief's §9 order ("list → search → Record") is the opposite, so shipping this needs an explicit accessibility order (not the default geometric one) to keep §9's rule — a small, real implementation cost, not a blocker. Dynamic Type: most resilient of the three — both rows are already full width, so the largest accessibility size only grows row height, never triggers a reflow. Thumb reach: Record spans the whole width, so it's reachable from a relaxed grip regardless of which hand holds the phone — the one variant that doesn't pick a side.
    Verdict: this is the strongest fix — Record and the field are no longer in the same row at all, so the submit-button reading disappears completely, at any Dynamic Type size or screen width. The cost is real: it's the tallest bottom chrome of the three (R7's "no letter sits under the field or Record, check with 27 letters" needs the most headroom back from home-index here), and it brings back a two-stacked-controls rhythm close to today's screen — though unlike the rejected model (b) shape, the field here still filters live, so it is not a reopening of that history, only a visual echo of it. Also carries the one VoiceOver-order cost named above.

    A2 — Record at the left, clear gap, field right

    record-button sits fixed at the row's leading edge; var(--space-lg) (16pt, double Option A's original 8pt gap) separates it from home-search-field, which flexes to fill the rest of the row. Typing swaps Record for cancel-search-button in the same leading slot.

    44pt: both controls stay 44pt; the gap itself is non-interactive, so it costs nothing for touch targets. VoiceOver order: visually Record reads before the field here too (left before right, in a left-to-right layout) — the same §9 order issue as A1, and for the same reason: whichever control sits visually first conflicts with "search, then Record," so A2 needs the same explicit order override. Dynamic Type: wraps to two rows at the largest size (Record above, field below, in that DOM order) — structurally converging on A1's shape under stress, but only at the largest sizes, not by default. Thumb reach: moving Record to the left edge is the one change here with a real, uncredited cost. Steven Hoober's thumb-zone mapping (cited in the brief, §5) puts the bottom-right corner in the natural/easy zone for a right-handed one-handed grip and the bottom-left corner in the stretch zone — the opposite is true left-handed. With no handedness setting (the brief's call 8, already answered: Apple's default, no setting), A2 trades the side that was easy for most people (right, under Option A and A3) for the side that's easy for fewer people. R1 says Record must be the most reachable control at rest; A2 is the only variant that puts that rule in tension with itself.
    Verdict: solves the proximity reading directly (a search field's "go" control is conventionally trailing, never leading, so Record on the left can't borrow that meaning), and keeps Option A's one-row chrome height — no new cost to home-index headroom. But it introduces a reach cost nothing asked for: Record moves out of the zone the brief's own cited research (Hoober) calls easiest for the majority grip, to satisfy a positioning worry that A3 can also solve without moving Record at all. Recommend only if the owner judges the proximity problem severe enough to accept that trade, or wants to revisit handedness later (brief's call 8 flags this as a V1.1 idea, not a V1 setting).

    A3 — Option A's order, now visibly separated

    Same left-to-right order as the original mock — home-search-field then record-button — but with a visible home-bottom-bar-divider (1pt, colors.line, decorative), a wider gap, and Record redrawn as a rounded rectangle (radius.control) instead of a pill, so its shape no longer echoes the field's own rounded ends. Typing swaps Record for cancel-search-button in the same trailing slot, same as the original mock.

    44pt: unchanged from Option A — field 44pt tall, Record 44pt tall, divider is decorative and non-interactive (no target-size implication). VoiceOver order: the only variant where the visual order already matches §9 "search, then Record" with no override needed — field is first in both the DOM and on screen, Record second in both. Dynamic Type: wraps to two rows at the largest size (field above, Record below, its own DOM order); the divider hides when wrapped since a vertical rule between two stacked rows stops meaning anything. Thumb reach: unchanged from Option A — Record stays at the trailing (right) edge, the easy zone for the right-handed majority grip the brief's Hoober citation describes; the left-handed stretch is the same one Option A already accepted and the brief's call 8 already declined to design around for V1.
    Verdict: the smallest change from the already-chosen Option A — same order, same chrome height, same reach profile, same VoiceOver order compliance "for free." The fix is real (shape + divider + gap break the "attached to the field's trailing edge" read that caused the proximity misreading) but it's a graded fix, not an absolute one: at a glance, or at normal reading distance, a gap and a shape change are a smaller signal than A1's full separation into two different rows. Worth user-testing (S4 in the brief: "did you know whether Andy would answer or just find names?") before treating this as fully resolved, where A1 would not need that test to be confident.

    Recommendation

    A3, with A1 named as the fallback if the owner wants the proximity question closed with certainty rather than reduced. A3 keeps everything Option A already won — lowest chrome height (most home-index headroom for R7's hardest check), the right-handed-majority reach the brief's own research cites, and a VoiceOver order that satisfies §9 without an accessibility-order override — and answers the owner's specific complaint with a shape and spacing change alone, the smallest edit that could still work. A1 is the strongest fix in absolute terms (two different rows cannot be misread as one control, at any type size or distance) and is the right call if the owner would rather spend the height cost than leave any ambiguity; it does cost real home-index headroom and needs the accessibility-order override to keep §9. A2 is not recommended: it trades a positioning worry for a reach cost that nothing in the brief asked for, when A3 reaches the same fix without moving Record at all. This is a design hypothesis, not tested behaviour — the brief's own S4 success criterion ("did you know whether Andy would answer or just find names?") is the test that would actually confirm any of these three closes the misreading; a TestFlight pass with A3 shipped is how to find out before investing in A1's extra height if it turns out not to be needed.

    Accessibility, shared across all three

    • home-search-field's only edge is colors.edge on paper, 3.2:1 (WCAG 1.4.11) — reused, unchanged by any variant.
    • record-button's moss fill with paper label text is an existing pairing (also confirm-dialog-action, calendar-connect-button) already covered by __tests__/contrast.test.ts — not a new pairing in any variant.
    • Meaning never depends on colour alone: Record is always the word "Record" plus a filled background (R1 forbids an icon-only control); in every variant the field is additionally distinguished by its outline-only edge versus Record's solid fill, and A1/A3 add a second, non-colour cue each (a full row break; a shape change) on top of that.
    • Reduce Motion: entering/leaving search mode crossfades the bar's contents rather than sliding, in all three. A1's row collapse is the one with the largest layout shift (a whole row leaves) — implementation should crossfade opacity without animating the row's height, to avoid a reflow that Reduce Motion would otherwise still show as movement.
    • Toggle "largest accessibility size" above: A1 only grows row height; A2 and A3 both wrap their single row to two, each landing on Record above field / field above Record respectively (each variant's own DOM order, not re-sorted) — worth checking against the real home-index component on device either way, per R7.
