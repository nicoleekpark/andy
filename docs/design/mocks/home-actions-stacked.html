    The question this follow-up answers

    A1 fixed the proximity misreading completely (Record and the field are never in the same row, at any width), but it is the tallest bottom chrome of the three A-variants and puts Record visually before the field — the opposite of the brief's §9 order ("list → search → Record"), needing an explicit VoiceOver-order override to keep it. Both are named costs, not blockers, in home-actions.md's "Option A variants" section. The four explorations below each attack one of A1's three named costs — chrome height, the VoiceOver-order override, or the flat weight of two full-width bars — while keeping everything else about A1 unchanged.

    S1 — Oval Record, centred and content-width

    Record stays its own row above the field, but instead of a full-width pill it is a centred, content-width oval — horizontal padding space.xl each side of the label, same 44pt height, same radius.pill shape token, same moss fill. The Voice Memos / camera-shutter family: a round control reads as *the one special action* rather than another bar.

    Principle: Von Restorff — a shape that breaks the rectangular rhythm of the field below it is the one thing the eye lands on, doing visually what A1 already does structurally (Record is never "in" the field's row). Resting: oval centred above the full-width field. Typing: the oval row crossfades out exactly as A1's record row does today, same mechanism. Offline: unchanged — the field still filters, home-ask-row still shows the C6 sentence. Largest Dynamic Type: the oval grows to full width at the largest size (shown in the toggle above), converging on A1's exact shape under stress — a graceful fallback, not a separate design to maintain. 44pt: height unchanged from A1; width is content-driven (no raw pixel width — padding token only), so it stays comfortably above the 44×44pt floor at any label length. VoiceOver order: unchanged from A1 — Record still reads visually before the field, so the same explicit order override is still needed; S1 does not touch this cost. Thumb reach: a centred target is neutral for either hand, same as A1's full-width Record — reachable by sliding the thumb to centre rather than to an edge, the same tap-anywhere-on-a-wide-target ease A1 already has, just over a narrower band.
    Verdict: the lowest-risk, purely cosmetic move of the four — it answers "the weight of two bars" by making one of them stop reading as a bar at all, costs no chrome height (same 133pt total as A1) and touches no business rule, copy or accessibility order. It does not fix A1's VoiceOver-order cost or its chrome-height cost — those are still open if S1 ships alone.

    S2 — Compact panel, tightened spacing

    Same two full-width rows, same order as A1, but drawn as one panel: a 1pt horizontal hairline (home-bottom-bar-divider, already proposed for A3, here laid flat instead of upright) replaces the open gap between rows, and the panel's own vertical padding moves from space.sm (8pt) to space.xs (4pt) at the top and around the divider. No new token — this is the existing scale read more tightly, the same move STYLE.md already describes for "existing screens move onto the scale as they're touched."

    Principle: Gestalt common region — a shared background and a single shared edge read as *one* control (a panel with two rows) rather than two independent bars stacked with a gap, which is the more literal fix for "the weight of two full-width bars." Resting / typing / offline: identical behaviour to A1, only the spacing and the divider differ. Largest Dynamic Type: both rows are already full width, so — like A1 — the size grows row height only, no reflow; the divider's opacity is reduced slightly at that size so it doesn't compete with larger text. 44pt: both controls stay exactly 44pt tall; only the *panel's own padding* shrank, never a tap target. VoiceOver order: unchanged from A1 — Record still visually precedes the field, same override still needed. Thumb reach: identical to A1 — full-width Record, neutral for either hand.

    Chrome height, computed from this mock's own CSS: A1 = border(1) + pad-top(8) + record row(44) + gap(8) + search row(44) + pad-bottom(8+20 safe area) = 133pt. S2 = border(1) + pad-top(4) + record row(44) + divider(1) + search row(44) + pad-bottom(4+20) = 121pt — 12pt less, handed back to home-index headroom for R7's "27 letters at the largest Dynamic Type size" check. An approximation from this mock's own CSS, to confirm against the shipped home-index component on device, the same caveat the brief's own Option A recommendation already carries.

    Verdict: the only variant that directly reduces chrome height, by a real if modest 12pt (~9%), at zero new tokens and zero behaviour change — it is a tightening, not a redesign, and is compatible with any of S1/S3/S4 (stack it with whichever shape or order the owner picks). It does not touch the VoiceOver-order cost or the "two bars" weight on its own (the hairline helps a little, by visually binding the rows together, but it's a smaller signal than S1's shape change).

    S3 — Scroll-aware Record

    At rest, identical to A1. While the list is being actively scrolled — not searching, just browsing the A–Z list — Record's row steps aside (crossfades out, 180ms), the same way it already does for typing, and reappears once scrolling settles. This gives home-index its full headroom back exactly during the one interaction most likely to need it: flicking through a long alphabetised list. iOS's own Safari and Mail compact or hide their bottom toolbar on scroll and bring it back on scroll up or at rest — the same learned pattern, not a novel one (Jakob's law).

    Resting: full A1 chrome, 133pt. Actively scrolling (toggle above): Record's row hides, leaving only the field row — border(1) + pad-top(8) + search row(44) + pad-bottom(28) = 81pt, a temporary 52pt of headroom back, only for the duration of the gesture. Typing: unchanged from A1 — the same hide, same trigger as before; this variant adds a second trigger, it doesn't change the first. Offline: unchanged. Largest Dynamic Type: the scroll-triggered hide is disabled at this size (toggle "list (S3 only)" has no effect once "dynamic type" is set to large) — a person relying on the largest text is relying on deliberate, predictable chrome, not a control that comes and goes. 44pt: never shrunk — this variant only ever fully shows or fully hides Record's 44pt target, never a smaller "compact" version of it still meant to be tapped; a shrunk-but-tappable control is a worse half-measure than a clean hide. VoiceOver order: same override as A1 needed whenever Record is present; while scrolling and hidden, the control is also removed from the accessibility tree (not just visually), so VoiceOver never lands on it then either. Reduce Motion (toggle above): the hide/show still happens, but instantly — no crossfade, following the same rule the brief already states for the search field's own expand/collapse.
    Risk, named plainly: R1 says Record must be "visible without scrolling... at rest." Hiding it while scrolling is a reading of "at rest" this brief never tested, not a settled answer — and it has a real cost: the exact moment someone spots a name while flicking through the list is also the exact moment they might want to hit Record, and this variant removes the control for that moment until scrolling settles. This needs explicit sign-off from `product-strategist`/the owner on that reading of R1 before it is buildable, not a default to ship quietly. It is also the only variant here with new, non-trivial state (a scroll listener, a settle-timeout, an accessibility-tree toggle) — real build cost the other three don't carry.
    Verdict: the most ambitious answer to the chrome-height cost — strictly better than S2's 12pt during the moment it matters most — but the only one that reopens a business rule's wording and carries a genuine, named reach risk. Worth prototyping on device and testing against the brief's own S1 ("the owner reaches Record without shifting grip") and S5 ("no mis-taps... no accidental Record when reaching for search") before committing, not a safe default.

    S4 — Swapped rows: field above, Record last

    The field's row moves to the top of the stack; Record's row becomes the very last, bottom-most element of the screen. Nothing else changes — same two full-width rows, same heights, same hide-on-typing mechanism, just reordered.

    Principle: this is the one variant that makes the required VoiceOver order the default geometric one, not an override. The brief's §9 asks for "list → search → Record"; visually, that is now top-to-bottom exactly as drawn — field directly under the list, Record last. No accessibility-order override to write, test or keep in sync with a future redesign. Resting: field row, then Record row, both full width, 133pt total — unchanged height from A1. Typing: Record's row hides exactly as in A1; the remaining field row stays pinned to the bottom of the screen (the bottom-bar-wrap is still the last flex child of the screen, so a shorter bar is still flush bottom, not floating mid-screen). Offline / largest Dynamic Type: identical to A1 in every other respect. 44pt: unchanged. Thumb reach: this is the one variant with a second, uncredited win worth naming directly: the brief's own Hoober citation (§5) calls the literal bottom edge of the screen the single easiest reach for a one-handed grip, in either hand. In A1, that literal edge is occupied by the field — the free, secondary action — while Record, the control R1 says must "win any conflict for the most reachable, most visible spot," sits one row above it. S4 puts Record on that literal edge instead, which is arguably closer to what R1 already asks for than A1 itself is.
    Verdict: the only variant that removes the VoiceOver-order cost outright (not reduces it) and brings Record into the single most reachable position on the screen, at the same chrome height as A1 — the strongest result-to-cost ratio of the four on the metrics A1's own write-up named. The one thing it gives up, stated plainly rather than decided here: the field no longer sits at the literal "very bottom" position the owner specifically liked about A1 (the iOS 26 Notes/Mail search placement cited in the brief's §5). It is still part of the same unified bottom chrome, directly above Record, not buried — but it is one row higher, and that is a real trade against a position the owner named, not a free win. Flagging for the owner's eyes rather than resolving it here.

    Recommendation

    S4, with S2's tightened spacing stacked on top of it (they don't conflict — S2 is a spacing change, S4 is an ordering change; nothing stops shipping both at once, at 121pt with no VoiceOver override). Together they answer two of A1's three named costs outright — the order override and a real slice of the chrome height — while changing nothing about copy, model, or any business rule's behaviour, only the brief's own observation about which row sits where. The one thing this combination gives up, repeated from S4's writeup: the field leaves the exact "very bottom" position that was part of why A1 was picked over Option A's single-row shape. If the owner weighs that position as non-negotiable, S1 is the safe fallback — zero behaviour change, answers the "two heavy bars" complaint on its own, and can also be combined with S2's spacing. S3 is the one with the largest upside (headroom exactly when scrolling needs it most) and the largest open question (a reading of R1 that needs the owner's and `product-strategist`'s sign-off before it's buildable, plus real new state to build and test) — worth a follow-up only if the owner wants to pursue it deliberately, not a default. This is a design hypothesis, not tested behaviour — the brief's own S4 success criterion (confusingly numbered the same as this section's S4 variant; "did you know whether Andy would answer or just find names?") and S1/S5 ("reach... without shifting grip", "no mis-taps") are what would actually confirm any of this, on a device, not this mock.

    Accessibility, shared across all four

    • home-search-field's only edge is colors.edge on paper, 3.2:1 (WCAG 1.4.11) — reused, unchanged.
    • record-button's moss fill with paper label text is an existing pairing, already covered by __tests__/contrast.test.ts — no new pairing in any of S1–S4.
    • Every control stays at or above 44×44pt in every variant; S3 is the one variant that could have been tempted to shrink Record instead of hiding it, and deliberately doesn't.
    • Meaning never depends on colour alone: Record is always the word "Record" plus a filled background in all four (R1 forbids an icon-only control); S1 adds a shape cue, S2 adds a shared-panel cue, on top of that.
    • Reduce Motion: S1/S2/S4 introduce no new animation beyond what A1 already specifies (the crossfade on entering/leaving search). S3 is the one with genuinely new motion (the scroll-triggered hide) and its Reduce Motion behaviour is spelled out above — instant, not animated, never disabled outright, since the state change itself (hidden vs. shown) still needs to happen for the headroom gain to mean anything.
    • VoiceOver order is stated per variant above; S4 is the only one that needs no override at all. S1/S2/S3 each need the same explicit order (list → field → home-ask-row → Record) A1 already requires.
    • Toggle "largest accessibility size" above: S1's oval grows to full width (converges on A1's shape); S2's rows just grow taller, same as A1; S3 disables its scroll-hide outright at this size; S4 behaves exactly as A1 does, just reordered.

    Considered and set aside: a second "Type" entry beside Record

    The brief for this follow-up raised a possible fifth idea: a small secondary control beside Record that jumps straight to typing a note (the record screen already has type-instead-button for this, one screen in). Flagging this as a scope question rather than a fifth stacked variant: it would add a second capture entry point to home's chrome itself, which nothing in the home-actions.md brief asked for (§11's "Not in this brief" doesn't name it, but it also isn't in Should/Must Have), and R1 already requires Record to be the one, unambiguous primary action at rest — a second button right beside it works against Hick's law at the exact spot the brief asks to keep simplest. Not designed here; if the owner wants it, it needs its own brief from product-strategist first, per this project's Scope Discipline rule.
